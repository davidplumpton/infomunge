# Mind Map - InfoMunge

> **For AI Agents:** Start with overview nodes [1-5], then follow inline references. Keep this file compact, roughly 20-50 nodes. When behavior, workflow, mistakes, or user preferences change, update the relevant compact node instead of appending duplicate one-off entries.

[1] **Project Overview** - InfoMunge is a Go tool for transforming text data with DataWeave-inspired syntax. It parses inputs and headers, rewrites syntax, evaluates an AST, then formats output [3].

[2] **Repo Map** - Key entrypoints: CLI `cmd/infomunge/main.go`, CLI app `internal/cli/app.go`, WASM build `cmd/infomunge-wasm/main.go`, inputs `internal/io/input.go`, runner `internal/runner/runner.go`, preprocessor `internal/preprocessor/*`, evaluator `internal/evaluator/*`, formats `pkg/formats/*`, modules `modules/dw/core/*.im`, standalone playground `docs/playground/index.html`.

[3] **Execution Pipeline** - Flow: CLI -> Inputs -> Header -> Preprocess -> Evaluate -> Format output. Header directives are parsed in the runner, preprocessing rewrites DataWeave-like syntax, evaluator executes builtins and lazy values, then output formatting serializes the result.

[4] **User-Facing Modes** - CLI accepts scripts directly or with `-f`, supports repeated named `-i` inputs, and can run loopback-only server mode via `./infomunge --server`. The playground posts scripts and inputs to `/run`; network-facing binds require `--api-key` [31].

[5] **Formats** - Format readers/writers live in codec-local `pkg/formats/*.go` files and register MIME types/extensions from their `init` functions through `pkg/formats/registry.go`; option handlers and MIME aliases register through `pkg/formats/options_dispatch.go`. Central read/write dispatch always resolves and invokes the selected codec, including for empty input and null output, so MIME validation and codec-specific semantics are never bypassed. `docs/FORMATS.md` is the user-facing registry and fidelity matrix, including the distinction between structured codecs and raw passthrough; its consistency test must change with registrations. JSON and NDJSON decode integer tokens to exact runtime `int` values, reject integer-shaped tokens outside that range, and keep decimal/exponent tokens as finite `float64` values. Java properties are input-only, CSV output requires an array of objects, and YAML input is exactly one document: its streaming decoder rejects trailing documents while active-path tracking rejects recursive aliases without breaking reusable aliases or merges. XML input uses `encoding/xml` as its sole syntax authority while applying explicit depth, element-count, per-element attribute-count, and per-element text-size limits during token consumption. XML output is also exactly one document root: validation rejects multiple or missing roots, invalid resolved element/attribute QNames, invalid namespace declarations, and unbound prefixes before ordered rendering.

[6] **Preprocessor** - Syntax transforms live in `internal/preprocessor/*`. Add operators in `internal/preprocessor/transformers_*.go`, then register an ordered phase/loop/mapping contract in `internal/preprocessor/stages.go` under the lifecycle defined by `internal/preprocessor/transform_contract.go`; be careful around bracket/brace scanning, grouped operands, and source mapping. Method-call transformers such as `value scan(pattern)` do not imply support for bare infix syntax such as `value scan pattern`; when parity is required, verify and test both transformer paths. Configured binary contracts derive bidirectional scan boundaries from declared precedence: left scans cross same- and higher-precedence raw operators, while right scans stop at same- and lower-precedence operators, preserving left associativity without splitting tighter expressions. Typed `as`/`is` left scans treat functional infix operators as boundaries only at the candidate operand's top level, preserving operators inside explicit groups and strings. Collection-family operators such as `find`, `splitBy`, and `joinBy` bind more tightly than comparison-family `contains`, `match`, `matches`, and `scan`, so comparisons consume the completed collection result regardless of transform execution order. Collection operators bind less tightly than additive expressions, so their structural left scan includes a complete `+`, `-`, `++`, or `--` source while the lambda-body scan keeps downstream additive expressions inside the lambda. Selector transforms run before functional transforms and therefore share a collection-lambda boundary scan so filter, range, recursive, and metadata selectors consume only the operand inside a raw lambda body; grouping a completed collection keeps a following selector at the outer level. Once a collection lambda is complete, configured infix operators such as `++`, `--`, `joinBy`, `contains`, `matches`, and `mod` apply to the collection result; ordinary arithmetic, comparisons, logical operators, `as`, and `is` remain in the lambda body. Nested collection lambdas are rewritten inside-out so inner `$`/`$$` bindings remain distinct from outer bindings; `mapObject` participates in this implicit-lambda pass with `$` bound to the value and `$$` bound to the key. Constant collection bodies are still lambdas, and an arrow nested inside an implicit body does not make that outer body explicit. A collection expression remains in a grouped explicit arrow body; compatible collection literals, complete calls (including rewritten conditionals), and collection concatenations keep a following collection operator inside an ungrouped explicit body. Array and object literals only claim operators supported by their source kind, while scalar or predicate bodies preserve InfoMunge's unparenthesized outer chaining. A fully parenthesized completed body makes a following collection operator outer. Infix `joinBy` and `splitBy` stop before a following same-depth `++`, while parentheses keep concatenation inside a delimiter expression. DataWeave infix `mod` is left-associative, binds above `default`, null-chain, range, and keyword collection/comparison operators, and binds below logical, native equality/ordering, type, additive, and multiplicative operators; its custom scanner therefore includes native logical/comparison and arithmetic expressions on both sides. Implicit `$`/`$$` replacement is syntax-aware and shared with filter selectors: ordinary lambda strings interpolate with language string coercion, while quoted regex pattern/flag payloads remain literal.

[7] **Evaluator** - AST evaluation and builtins live in `internal/evaluator/*`. New builtin handlers usually belong in `internal/evaluator/builtins_*.go` and must have a matching dispatch/metadata entry in `internal/evaluator/builtin_specs_*.go`; add a new spec group to `defaultBuiltinSpecs` only when introducing a category. Direct ordinary, module-qualified, and try-family user-function calls share `invokeUserLambda`, which enforces exact arity and evaluates against the captured lexical environment with only explicit parameter bindings; do not add separate invocation helpers. Collection operations are the intentional exception to exact invocation arity: array callbacks may declare the prefix they need from `(value, index)`, and object `mapObject`, `filterObject`, and `pluck` callbacks may declare the prefix they need from `(value, key, index)`. Module wrappers that expose those callback shapes should pass callbacks directly into collection operators; wrapping one in a narrower lambda discards supplied arguments and restores exact ordinary-call arity. Scalar, array/XML-multi-value, object, coercion, and assertion equality share the exact cycle-safe recursive comparator in `internal/evaluator/equality.go`; do not reintroduce `reflect.DeepEqual`, lossy `float64` conversion, or display-string equality shortcuts. Numeric builtins preserve runtime integers, use exact rational aggregation/comparison where needed, and report precision loss or range overflow instead of silently converting large integers to `float64`. Array string selectors collect matching fields from immediate object elements, skip missing or non-object elements, and return `null` when no match exists; presence reports whether any element matches, assert fails only when none match, and recursive descent follows the same `null`-on-no-match rule while traversing nested arrays and objects. Dot-notation presence/assert selectors are rewritten through `__presenceSelector`/`__assertSelector` into typed internal selector operations; ordinary bracket strings always remain literal keys even when they end in `?` or `!`. `reduce` binds callbacks as `(item, accumulator)`; only a default on the second parameter initializes the accumulator, while a third index parameter remains an InfoMunge extension. Empty-array `max`, `min`, `maxBy`, `minBy`, and reduce-without-default return `null`; reduce with an explicit accumulator default returns that default. Null sources propagate through `sizeOf`, `flatten`, `map`, `filter`, `flatMap`, `orderBy`, `distinctBy`, `groupBy`, `pluck`, `mapObject`, and `filterObject`; `flatten` and `flatMap` remove exactly one direct array boundary rather than recursively flattening deeper arrays. Arrays-module null helpers skip callbacks and return `null`, except `some` and `every`, whose null identities are respectively `false` and `true`; `indexOf` and the join family intentionally have no null overload. Arrays-module `divideBy` normalizes its chunk size to `max(1, ceil(size))`, matching DataWeave for non-positive and fractional sizes while ensuring recursive progress. Arrays-module `slice` uses its own internal builtin to clamp negative `from` to zero, return empty for negative `until`, and clamp an oversized `until` to the array length; the generic array/string `slice` intentionally continues to resolve negative bounds from the end. Arrays-module `splitWhere` returns `{l: [], r: array}` when no item matches, including empty arrays, while null arrays return null without evaluating the callback. The special collection operators use an explicit shared null policy and skip selector-lambda evaluation, while `maxBy` and `minBy` intentionally continue to reject null. The `range(end)` builtin requires a finite, non-negative exact integer within the runtime integer range and emits exact runtime integers. The `to` builtin anchors results at the supplied start value and steps by one without truncating fractional bounds; range-selector indexes still intentionally truncate numeric indexes. Direct coercion to the exact-only built-ins `Array`, `Object`, `Function`, and `Regex` preserves an already matching value just as union coercion does; mismatches are coercion errors rather than unknown-type errors. Successful implicit value-to-string paths such as joins, dynamic/grouped keys, URL query values, and lazy display share `coerceToString`; never use direct Go formatting there because language null is spelled `null`, not `<nil>`. String operands to `contains`, `find`, `replace`, and `splitBy` always use literal text semantics; only explicit `Regex` values (or the legacy flagged `find` form) select regular-expression behavior. `match` and `matches` require a whole-input regex match; successful `match` results and every `scan` result row include the full match at index zero before capture groups. Array `--` with an array right operand removes every listed value, while a scalar right operand remains an InfoMunge extension that removes that one value. Object ordinal selectors use observable insertion order and resolve negative indexes from the end, matching array and string indexing. Preserve lazy evaluation and nondeterministic builtin behavior such as `now()`. When changing helper sentinel semantics, audit every caller conversion as well; for example, an invalid `inclusiveRangeBounds` result must become `null`, not a typed empty value. When migrating value/error checks from `RunString` to `ExecuteString`, call `ExecutionResult.Resolved()` before treating execution as successful because lazy/stream errors can surface during resolution.

[8] **Runner And Modules** - Runner orchestration is in `internal/runner/runner.go`; module loading behavior is in `internal/runner/module_loader.go`. Core module scripts live under `modules/dw/core`.

[9] **Testing** - Cucumber tests run with `go test -v ./test -timeout 5m`. Add or update cucumber coverage for new or changed user-visible behavior; use focused Go unit tests for internal behavior and refactors. Feature files live under `test/features` from the repo root; use `GODOG_PATHS=features/...` because the test harness resolves feature paths relative to `./test`. The DataWeave differential harness supplies named inputs through `.json` files so the CLI can infer their MIME type, strips only its known `DW_HOME` startup warning, rejects other unparseable stdout, reports generated/error/comparison outcomes, and requires at least 20% of its budget to reach structural comparison. For preprocessing audits, call `PrepareForParsing` with `Options.TraceTransforms`; `RunnerOptions` does not expose transform tracing, and `TransformTraceEntry` records source in `Before` and `After`.

[10] **Quality Gates** - Prefer targeted tests for the changed layer. Use `INFOMUNGE_SKIP_GODOG=1 go test ./... -timeout 5m` for the bounded repo-wide package suite, then run cucumber separately when user-visible behavior changed. In restricted workspaces, set `GOCACHE` to the repository-local `tmp/go-build-cache` on the first Go command instead of waiting for the default cache to fail; this applies to every Go-invoking Make target and focused Cucumber command, after the known cache mistake recurred in both differential and focused feature runs. The full cucumber suite includes `httptest` loopback servers, so rerun it outside the sandbox when local port binding is denied rather than treating that environmental failure as a product regression. For documentation- or workflow-only edits, validate the affected commands, links, examples, or formatting; cucumber is unnecessary unless runtime behavior changes. The mutation corpus soak is skipped by default, differential testing runs 50 external comparisons by default, and larger budgets run explicitly with `INTENSIVE_TEST_SOAK=1`.

[11] **Version Control** - Use `jj` only; never use git commands. Commit with `jj commit -m <description>` and do not use `jj new` with a message. Run JJ commands sequentially because status/describe/commit can touch working-copy state and ref locks. `jj diff` has no `--check` flag; use targeted text checks for whitespace validation.

[20] **Memory Hygiene** - Keep this file compact. Merge repeated pitfalls into category nodes, preserve prevention steps that materially change future behavior, and avoid growing a dated entry for every recurrence unless the recurrence reveals a new prevention rule.

[21] **Patch Discipline** - Use the dedicated `apply_patch` tool for manual edits, including temporary helper source; do not create files through shell redirection or invoke patching through shell commands. Keep broad refactors in small hunks and reopen edited regions before testing. When replacing the last call from a Go package in a file, remove its now-unused import in the same patch; `gofmt` does not remove imports. Reflection-based Go AST rewrite helpers must track visited pointers (or explicitly skip object/scope links) because identifier resolution metadata makes the AST graph cyclic. In Go, declare byte slices and source-mapping integer slices separately before multi-assignment; a grouped declaration gives every name the same element type.

[22] **Search Discipline** - Use `rg` first for searches. Put all flags, including `-g`, before paths; put `--` before the pattern when the pattern may begin with `-`. Before executing a constructed search, check that every `-g` appears before `--` and the pattern. Use `rg --files` to confirm unfamiliar filenames before passing them to `sed`; do not let one guessed path abort a command containing otherwise useful inspections. Check the file type before sending an external executable resolved from `PATH` to a text reader because the command may be a compiled binary. Run discovery and inspection as separate calls so the inspection copies the exact returned path instead of guessing a sibling filename before seeing discovery output. Use `rg -U` only when true multiline matching is needed. Use `--no-filename`, not `-h`, when suppressing filenames because this `rg` treats `-h` as help. Let a no-match search return status 1 instead of masking it with a chained `|| true`, and do not gate unrelated formatting or test commands behind a search whose no-match result is acceptable. When `rg -r` is used as an extractor, match the entire input line or unmatched suffix text will remain in the replacement output.

[23] **Stateful Command Discipline** - Do not parallelize beads mutations with reads (`br update`/`br close` then `br show`), and do not parallelize any JJ operations, including read-only help/status/diff discovery commands. Never place a JJ command inside `Promise.all` orchestration or a multi-command `exec_command`, even during initial context gathering or when every sibling is a read-only file inspection; this mistake recurred in the 2026-07-26 `bd-32q3` and `bd-38uz` sessions while bundling `jj status` with requested README/AGENTS/MIND_MAP reads. Before constructing any initial orchestration array, run `jj status` alone in a direct shell call and reject any orchestration element whose command begins with `jj `. Inline repository instructions do not make the first context-gathering call an exception: the first invocation may be `jj status` alone, followed by guidance reads in a separate call. Use exactly one JJ invocation per shell call, and run it separately from other shell work, because even read operations snapshot the working copy and may require VCS metadata write permission. Run state-changing and state-inspecting VCS/beads commands sequentially. Run formatting, tests, cleanup, searches, and inspections as separate commands instead of joining them with shell control operators such as `|`, `&&`, `||`, and `;` or with multiple newline-separated commands; this applies even when each command is read-only, including piping `rg` into another `rg`, which also recurred during `bd-32q3`. Before every shell call, reject command text containing `|`, `&&`, `||`, `;`, or more than one command line, then split each segment into its own call; apply this checklist to the initial context-gathering pass too. When a long-running command yields, preserve its session or cell ID and poll that same process through completion; do not discard the handle or infer success from partial output. Never wrap a long gate in orchestration unless the wrapper explicitly captures and polls every returned process handle; use a direct command call by default. The `functions.exec` orchestration tool accepts raw JavaScript, not a JSON command object; call `tools.exec_command({...})` inside it and surface the result.

[24] **Shell Quoting And Variables** - Avoid backticks inside double-quoted shell commands; they still execute command substitution, including in `rg` patterns. Use single-quoted patterns when searching for Markdown code spans. Never place wildcard paths in shell arguments, including inside brace-expanded path lists; express file selection with `rg -g` because zsh rejects unmatched unquoted globs before `rg` runs. Ordinary single quotes preserve `\n` literally, so pass multiline CLI scripts with zsh ANSI-C quoting or a file when real newlines are required; JavaScript `JSON.stringify` is not a substitute because its quoted shell argument passes literal backslash escapes. Do not try to preserve embedded single quotes by doubling them inside a single-quoted shell argument; the shell removes them. Avoid complex inline shell quoting for beads descriptions, and use a safely single-quoted description with no embedded apostrophes or a temp file under `tmp` when literal quotes or multiline payloads are needed. Never embed JSON-stringified Markdown, scripts, or probe expressions in a shell command: zsh still executes backticks and expands `$` forms such as `$$`, silently changing the tested program or damaging a ticket. Single-quote the complete script with a deliberate embedded-quote escape or use a temp file. In zsh, never use `path` or `status` as scratch variables because they are special parameters that can break command lookup or abort assignment; use task-specific names instead. Zsh parameter-removal operands are glob patterns, so avoid unescaped literal brackets there; use a simple text tool when stripping punctuation-heavy delimiters.

[25] **Cucumber Harness Pitfalls** - CLI failure scenarios usually need `Given the following input content`, while in-process runner scenarios use `Given the following script`. For multiline fixture files, use docstring-backed steps so real newlines are written. `GODOG_PATHS` is resolved from the `test` package directory, so focused paths start with `features/`, not `test/features/`. Check `test/godog_test.go` before introducing assertion wording: the harness registers `the error should contain` and `the output should not contain`, but not `the error should not contain`.

[26] **Script Formatting Pitfalls** - Keep complex function calls in cucumber scripts on a single expression line unless multiline parser coverage exists. Parenthesize repeated unary minus (for example, `-(-1)`) because adjacent `--` is not parsed as two negations. Documentation snippets intended to run as standalone CLI scripts need a header and `---` separator. JSON output expectations are exact text comparisons, so match compact serialized output; Go's JSON encoder renders `<`, `>`, and `&` in strings as `\u003c`, `\u003e`, and `\u0026`.

[27] **Parser Fragility Notes** - Inline `if` expressions inside object literals and dense object-value expressions have repeatedly hit brace/branch scanning bugs. For unrelated coverage, use simpler objects, arrays, defaults, or isolate conditionals in parser-specific tests.

[28] **Generated Test Data Pitfalls** - Property-generated source literals should avoid scientific notation and parser-active string sequences such as interpolation-looking `$(` unless explicitly testing those paths. Fixed-precision float generators used by byte-stable JSON round-trip properties must normalize a rounded `-0.000000` to `0.000000`, because JSON integer-token decoding deliberately maps the writer's `-0` representation to exact `int(0)`. Differential strings use a shared plain-ASCII subset because Go escapes such as `\a` do not have the same meaning in DataWeave. Differential collection generation covers nested collection forms; computed array sources include function calls, concatenations, and conditionals, while `pluck` and `mapObject` use object sources. Differential `reduce` uses a two-parameter accumulator-returning callback so it exercises callback order without unrelated type/operator mismatches. Keyed index generation covers both the root payload and nested payload fields after array selector compatibility was aligned. Differential `+` must be operand-type aware: numeric-looking strings paired with numbers share coercion semantics, but InfoMunge's nonnumeric string-concatenation extension is not generally a safe DataWeave-side skip because DataWeave accepts an array-left operand as array append and returns a structurally different success. Do not assume numeric source literals evaluate as `float64`; assert the runtime representation when an error test exposes Go types (whole-number literals can be `int`).

[29] **Error Context Discipline** - When changing or asserting wrapped error messages, inspect the final rendered CLI stderr/output instead of inferring wording from helper names, and preserve essential context such as filenames. Common evaluator errors stay typed as `errors.Error` and carry an unresolved generated token position until `sourcemap.Map.FormatEvalError` maps it to original line and column; their direct `Error()` text includes the `EvalError: ` prefix, so focused unit assertions must account for it. Do not resolve AST positions through an empty file set or reintroduce `:0:0`.

[30] **Context Refactor Discipline** - Preserve existing public/internal call signatures where practical by adding context-aware variants first, then migrate call sites incrementally to reduce compile fallout.

[31] **Server Exposure Safety** - HTTP server mode defaults to `127.0.0.1:8080`. Unauthenticated server mode accepts only loopback listen hosts; configuring a non-loopback or wildcard address requires `--api-key` because `/run` evaluates caller-supplied scripts.

[32] **Object Order** - `Object` remains a map alias for API compatibility. Order-aware construction uses `values.NewObject` plus `values.SetObjectValue`; observable iteration uses `values.ObjectKeys`, which preserves tracked insertion order and alphabetically sorts legacy untracked maps. Structured readers and object-producing evaluator paths must propagate this metadata, while structural equality remains order-insensitive. The metadata registry uses allocation-aware weak map identities, runtime cleanup callbacks, and opportunistic dead-entry sweeps so it does not retain maps, accumulate reclaimed entries, or confuse a recycled address with its prior allocation. Registration is internal to construction and first insertion; do not add a public order-metadata mutation seam without a concrete caller.

[33] **Assertion Result Semantics** - `must(value, matcher)` returns the successful `MatcherResult` object (`{"Success":true,"Message":""}`), while `assert` and `assertThat` return the asserted value. Cucumber output expectations must reflect the chosen assertion API.

[34] **Evaluator Test AST Fixtures** - Builtins that validate arguments may call `e.Pos()` even on successful paths. Direct builtin unit tests must use an `ast.CallExpr` with a non-nil `Fun` node (for example `&ast.Ident{Name: "sizeOf"}`); an empty call expression panics while resolving its position. Raw `Evaluate` tests for the user-facing `range` builtin must call its internal `__range` alias because `range` is a Go keyword rewritten by the preprocessor; Cucumber/runner tests should continue to use `range`.

[35] **Function Resolution** - Unqualified lexical function bindings resolve before both special and regular public builtins. Registered double-underscore implementation builtins resolve before lexical bindings because the preprocessor emits those names for generated syntax; user declarations must not intercept helpers such as `__default`, `__lambda`, `__map`, or `__coerce`. Embedded core wrappers whose exported names match public builtins must use the internal `__native` dispatcher instead of relying on builtin-first resolution.

[36] **Builtin Arity Contracts** - `BuiltinSpec.Arity` is authoritative: registry construction wraps eager and special handlers with positional, function-specific validation before invocation. Keep exact, optional, and variadic bounds aligned with the handler's intended public contract; the registry contract test rejects calls immediately outside every bounded declaration without executing handler logic.
